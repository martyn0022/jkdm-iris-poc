The canonical message the discipline

What it deliberately does not contain.

No partner vocabulary

No BGM, no TDT9C1, no UNH. If a canonical field is named after an EDIFACT segment, the abstraction has already failed and the next partner will not fit.

No backend vocabulary

No PIC X(35) widths, no COMP-3, no COBOL field names. The model does not know which implementation will answer.

Not everything the partner sent

The CUSCAR carries consignment refs, container counts, weights. The model does not. You map what consumers need, not what senders send — a model that absorbs every field of every partner becomes a superset nobody trusts, and every mapped field is one you must keep correct forever.

The cost of that discipline is visible this afternoon. The manifest lists individual consignments and the canonical message has nowhere to put them, so they are dropped. That is a real modelling decision with consequences — and exactly the kind that deserves a conversation with JKDM rather than a shrug.

The canonical message why WCO

It is borrowed, not invented.

The field names come from the WCO Data Model — your §4.3.5 and §6.12 both call for it.

That matters for a reason that is easy to miss: a canonical model invented in-house encodes whatever the first three partners happened to send. The fourth partner does not fit, somebody adds a field, and within two years it is a union of every dialect it has ever met.

Borrowing an international customs standard means the model was designed against hundreds of customs administrations before you saw it — and when a partner changes, the standard usually already has a place for it.

The test to apply

When someone proposes a new canonical field, ask:

1. Which consumer needs it? If none, do not add it.

2. Does WCO already name it? If so, use their name.

3. Is it partner-specific? If yes, it does not belong in the canonical form — it belongs in the partner's own mapping.

Flow B what the lock buys

The operations you must never run twice are exactly the ones it refuses.

Shadow mode discards the response. It cannot discard the side effect.

Shadow an operation that writes — lodging a declaration, posting revenue, issuing a receipt — and you have written twice. Throwing away the second answer undoes nothing.

Marking fiscal operations closes that for the cases that matter, because the operations that move money are the same ones that write. The dangerous half is designed out rather than managed.

Do not overclaim

Fiscal is a proxy for "has side effects", and they are not the same thing. A non-fiscal operation that writes would still double-write under SHADOW. Nothing checks that today, and whoever declares an operation is making that judgement by hand.

The defect nobody planted this

One cent, on one declaration, from seven lines of arithmetic.

COBOL

1088.47

Rounds each line to two decimals in packed decimal, then accumulates.

PHP

1088.46

Accumulates at full float precision, rounds once at the total.

Neither is a bug

Both are what a competent developer writes. It took running both against the same data to find it.

§5.7 carries this in a warning box: "Money is decimal, never floating point. COBOL packed-decimal fields (for example PIC S9(9)V99 COMP-3) map to integer minor units or arbitrary-precision decimals with explicit rounding, never to native floats."

Your architecture names the exact field type and prohibits the exact mistake — and it still happened, in code written by people who had read it. That is the argument for the gate being mechanical rather than a review checklist.

Still open

Lab · what you switched on after step 5

Everything already worked, except one step.

Lab the step that was never the problem

The fabric already knew it was a manifest.

Every EDIFACT message names itself on its second line, and the fabric reads that before deciding anything.

UNB+UNOA:2+DFTZ001:ZZ+JKDM:ZZ+260818:1030+000000903 UNH+000000903+CUSCAR:D:96A:UN <- the message says what it is BGM+85+MANIFEST-2026-0041+9

So UNSUPPORTED never meant "I cannot read this file". It meant "I know exactly what this is, and I have no handler for it."

Lab the routing decision

Three branches. Yours was the empty one.

Lab what the four lines do

Four coordinates in, four named fields out.

Lab why coordinates and not names

The names live in a dictionary nobody has licensed yet.

EDIFACT was designed in the 1980s for links billed by the character. Leaving field names out made messages far smaller. The cost is that a message is unreadable without the matching dictionary.

GetValueAt("2:2") → MANIFEST-2026-0041 by position — works today GetValueAt("BGM:2") → (empty) by name — needs the D96A dictionary

Load D96A and this same mapping becomes a drag-and-drop screen — you connect DocumentMessageNumber to ManifestRef and never type a segment number again. That is the version a business analyst maintains.

So the coordinates are a consequence of a missing licence, not how this is meant to be done. Small, real, and it has to land before the first partner conformance test.

Lab · Part 2 what shadow produces

One component held both answers. Nothing else in the estate does.

In SHADOW the fabric called both implementations, gave the consumer the COBOL answer, discarded PHP's — and compared them on the way past.

COBOL never sees PHP's answer. PHP never sees COBOL's. Postgres sees neither. So if anyone is going to ask whether they agree, this is the only place it can be asked.

But the fabric does not decide. Which differences matter arrives back as one small configuration class, so the report is readable and the rule is applied the same way every time.

vesselName padded 30 / trimmed eta +08:00 / +00:00 statusCode RL / RELEASED description cut at 40 / full backend COBOL / PHP

Five differences on one manifest. statusCode is classified fiscal because release status is named in the §5.7 list — a decision recorded in configuration, not made by the tool.

Close 17:00

Five open questions. None are blockers. All are cheaper to answer now.

  • How does IRIS invoke Visual COBOL? Undecided — four options with very different latency and transactional characteristics. Today's HTTP wrapper is POC convenience, not a recommendation, and it affects Wave 1 sizing.
  • Does file and batch traffic get strangler routing? §5.2 is silent. The POC says yes.
  • Shadow mode on writes. Closed for fiscal operations by policy; not solved in general.
  • X.400. §2.7 records the DFTZ link as X.400 · SFTP. IRIS speaks SFTP and EDIFACT natively, not X.400. Needs a gateway, a VAN, or a partner-side change — and the first question is whether any live traffic still uses it.
  • D96A schemas. Not in the product; licensed separately. They turn positional mapping into drag-and-drop, and they must land before partner conformance testing.
